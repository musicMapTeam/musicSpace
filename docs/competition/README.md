### 1.1 主稿 · 赛道二（创新音乐产品）

```text
解决什么问题：演唱会散场后，每个人的相册里只有自己站的那个位置：你拍到了舞台，身边的朋友记住的是人海和合唱。群相册能收齐照片，却分不清哪几张是同一刻，也很难只换想换的那一张。
解决方案：Music Space 让同场观众用现场卡交换彼此没有的视角。照片默认私藏，申请指向具体的一张卡，对方本人同意后才合成两人署名的双联票根。「同一刻」按照片自带的拍摄时间判断（相差 3 分钟内）；视角由一个在本机运行的小模型建议，判断时照片不上传，没把握不替你选，选什么由你定。两者一起配对出「同一刻的另一面」并写出理由。歌单按拍摄时间排序，每首可跳到 QQ 音乐搜索（不是站内播放）。
```

### 1.3 写法边界

- 只写已实现的行为：AI 只建议视角，视角与拍摄时间再由规则配对，理由由规则写出，不写成「AI 匹配」。
- 不写：获奖预期、用户数或留存这类没有的数据、AI 准确率（只在公开 CC 照片上量过）、跨设备交换（线上链接是静态版，真实房间在局域网或录屏里演示）、QQ 音乐的站内播放或对接。
- 示例角色、场次、歌曲和示例照片的拍摄时间是虚构的，预置图由 AI 生成；自填的场次、视角和照片不构成到场认证。

### 1.4 AI 使用说明（如需填写）

- **产品里的模型**只有一个：TinyCLIP-ViT-8M/16 的图像塔（MIT，int8，8.8 MB）加 onnxruntime-web，在浏览器里建议照片的视角，照片不上传。
- **不是模型**：配对、排序和理由是规则（`web/js/moment.js`）；歌单排序、QQ 音乐链接（URL 模板）、EXIF 读取都是普通代码。
- **开发与素材**：AI 辅助了方案梳理、研究、界面与代码实现；预置的两张示例现场图由 AI 生成（2026-09-26，虚构，来源记录见 `web/assets/image-provenance.json`）；团队负责产品取舍、内容筛选和实际检查。未使用的工具或模型不列作成果。
- 本节替换了旧稿里「没有模型推理，规则匹配不是模型推理」的说法，它在 0.16 已不符合现状。

## 4. 评委问答

**为什么不用共享相册或群相册？** 相册解决的是「收齐照片」，想要所有原图时它更直接（活动相册类产品也能让来宾上传和下载，见[社交产品研究](../../references/research/2026-09-27/social-product-review.md)）。Music Space 做的是另一件事：两个人各拿出一张，指向对方的一张，对方本人同意后共同署名，并且写明为什么这两张是同一刻的两面（拍摄时间相差几分钟，你拍舞台、TA 拍人海）。这一步是否值得多做，需要真实观众试用来判断；现在没有试用数据，不作断言。

**为什么用端侧 AI，它的边界在哪？** 视角标注是制卡里最费事的一步，所以让小模型替你预选。它在浏览器里跑，照片不上传，不需要服务器和调用费用（官方 FAQ Q6：不提供额外的 token 支持），线上的静态页也能用。它是很小的零样本模型（TinyCLIP-ViT-8M/16 图像塔，8.8 MB），会判错：只在有把握时预选，没把握给两项虚线提示、不替你选，你选的永远不被覆盖；配对、排序和理由是规则，不是模型。准确率只在 75 张公开 CC 照片上量过：spike 里 top-1 92%；应用自己的路径上 57 张判为「有把握」、全对，另 18 张「不确定」，它们的前两名里都含正确答案；再加六种退化共 525 个输入，402 个「有把握」、400 个对，错的两个是变暗和裁切后的舞台照。没有在真实观众的手机照片上量过，所以不当作产品准确率。代价：第一次要下载约 23 MB（GitHub Pages 压缩传输时约 10 MB：2026-09-30 用 curl 带 gzip 测过，五个文件共 10,344,436 B，浏览器实际协商的编码没测），之后存在浏览器里；`file://` 或不支持 WebAssembly SIMD 的浏览器里不出现 AI，视角自己选；手机上的耗时和内存没测。

**隐私怎么处理？** 照片默认私藏，只有主动展示的卡同场的人才看得到；申请指向两张具体的卡，对方本人同意后才交换，交换后是快照，改卡不改旧快照，删除只删自己那一份。静态演示里，自己的照片缩小并去掉定位信息后只存在这台设备的浏览器里，不进房间、不上传；AI 判断在本机进行，模型文件从本站下载一次，照片不出设备。房间版里，点「保存」时照片才上传到房间服务（SQLite），读取受身份和卡片 / 交换权限控制；AI 判断本身不上传。拍摄时间在压缩前从原图读出。身份是匿名的，只保存在当前浏览器，清除网站数据后无法找回。自填的场次和照片不构成到场认证。

**为什么线上是静态版？** 评委要能直接打开、评审期间一直可用：GitHub Pages 是静态托管，不用维护服务，也没有账号。静态版里有本地双角色示例（Lin / 阿遥），能走完制卡、同一刻、申请、同意、双联票根、歌单的全流程，也能换成自己的照片。真实房间需要 Node + SQLite、持久磁盘和 HTTPS，我们在局域网或录屏里演示，线上不声称支持跨设备交换，页面上也这样写。

**冷启动怎么办？** 不做全城陌生人匹配，从同去一场演出的朋友或活动小圈开始，两个人就够。一个人先有价值：私藏的现场卡、单卡票根 PNG、按拍摄时间排的歌单。但「有人愿意主动发起交换」没有验证过：没有目标用户试用，「同一刻」还要求另一位观众的照片拍摄时间与你相差 3 分钟内，没有这样的人时就只有单人价值。试用计划见第 2 节。

**QQ 音乐在哪里用到？** 「那晚的歌单」里每首歌带一个 QQ 音乐的按歌名搜索链接，不是核实过的同一录音的直达页，也不保证是当晚唱的版本；QQ 音乐的手机页会丢掉搜索词，所以另有「复制歌名」。页面没有内置音频、歌词或专辑封面，不称站内播放，与 QQ 音乐没有任何对接。

## 6. 评分维度对照（官方没有公布权重）

官方评审细则是三个维度，没有给权重（[原文](../../references/official/2026-09-26/spreadsheet/05-scoring-cells.md)）。下面只是把已有的材料对到维度上，也写出还拿不出的东西；它不是打分，不据此推算获奖概率。

| 维度与官方描述 | 我们能拿出的 | 目前拿不出的 |
| --- | --- | --- |
| **用户价值**：「考察作品是否真正打动用户、解决某个真实的音乐或音频场景需求，能否带来清晰、有趣、自然的产品体验，并为用户创造实际价值」 | 散场后「补全自己记住的那一晚」这个场景；一个人也有收益（私藏的卡、单卡票根 PNG、歌单）；两个人的交换有具体动作、对方同意和写明的理由；静态版能在浏览器里走完全流程 | 没有目标用户试用，没有「愿意主动交换」「比群相册更愿意用」的证据；没有留存或转化数据 |
| **可行性**：「考察作品是否具备合理的产品逻辑和技术实现路径，Demo 完成度是否达到预期，是否具备进一步落地和持续发展的潜力」 | 静态页加端侧小模型加规则配对，不依赖外部 API 与 token；`npm test` 三份检查通过；房间版（Node + SQLite）在同一台电脑的两个来源之间走通；模型、运行时和标签同源自托管，来源与许可可复现 | 真机、微信和大陆网络没测，AI 在手机上的耗时与内存未知；含 AI 的构建还没上线；真实观众照片上的准确率没量；QQ 音乐只有搜索链接 |
| **创新性**：「解决方案切入角度是否新颖，作品是否提出了突破性的思路」 | 切入角度：交换「视角」而不是收齐照片；用拍摄时间判断「同一刻」、用视角判断「另一面」，并把理由写给用户；视角建议在本机完成 | 不声称首创，也没有做竞品优劣结论；「比相册值得多一步」没有用户数据 |
