# Livehouse 房间 · 第一条真实数据链路

2026-09-30。本轮是同仓库的新增房间系统，不把既有 avatar 合影邀请当作多人现场房间。尚未发布。

## 已实现并在本地验证

- 使用 `/api/avatar/session` 的独立匿名身份；昵称不等于登录凭证
- 开场人创建房间，创建/加入都要求明确同意展示昵称与小人
- 60 位随机熵的 12 字符口令；未加入者只能读取场次元数据，不能读取名单或照片
- 最多 24 个有效成员；每人每场最多保留 6 张照片
- 上传必须明确选择 `private` 或 `members`，JPEG 经校验与元数据清理
- 成员照片读取同时检查请求者和上传者的有效成员身份；对象存储地址不公开
- 离开后，共享上传转为私密；再次加入不会自动重新共享
- 24 小时入口期限；关闭/过期禁止新加入和新上传，已有成员仍可读取先前获准内容
- 上传者离开后仍可访问个人照片库、撤回分享或移除照片
- 离开的开场人保留自己房间的元数据和关闭权限，不因此得到成员名单或他人照片
- 幂等重试、条件写入、乐观版本检查；提交结果不确定时不删除可能已被引用的图像
- 个人房间（包括本人已离开的历史场次元数据）和照片列表采用权限限定的游标分页

Node 适配器把图像放在独立 avatar SQLite 文件的私有表中；Worker 适配器使用 D1 与私有 R2。两者共用同一权限处理程序。旧 `/api/live` 和 `/api/avatar` 的能力、数据文件及根站不被替换。

## 运行与测试

`npm run test:event` 运行 10 个 Node/SQLite 与 23 个 Worker/D1-SQLite/private-R2 测试，共 33 项。`npm test` 的旧主线断言继续通过。

覆盖独立身份、跨房间拒绝、24 人容量并发、6 张照片上限、私密和成员权限、退出/撤回、关闭后的保留、重启恢复、原重试编号恢复、存储故障、提交后丢包、权限撤回期间的图像读取、分页与共享出口 IP 的正常请求。

共享 IP 测试使用 24 个模拟成员，每 5 秒刷新并各读取 6 张图片。限额是原型保护值，不是生产承载量承诺：每 IP 1800 次/分钟（v2新增社交轮询后校正）、口令预览 120 次/分钟；每身份读取 180 次/分钟、写入 40 次/分钟、加入 20 次/分钟、上传 20 次/小时、创建 6 次/日。

追加迁移为 `runtime-preview/drizzle/0001_event_rooms.sql`。已应用的 `0000` 迁移和原快照没有改写。新的迁移尚未用于公开运行环境。

## API 摘要

前缀 `/api/event`。除健康/口令元数据预览外均需要 bearer 身份；修改需要 `Idempotency-Key`。

- `POST /rooms` 创建；`GET /rooms` 个人参与/管理列表
- `GET /preview/:code` 元数据；`POST /rooms/:code/join` 明确加入
- `GET /rooms/:id` 成员房间内容；`POST /rooms/:id/leave` 离开；`POST /rooms/:id/close` 关闭
- `POST /rooms/:id/photos` 明确上传可见性
- `PATCH /photos/:id` 修改可见性；`DELETE /photos/:id` 撤回并移除
- `GET /photos` 个人保留库；`GET /photos/:id/image` 每次检查权限后读取
